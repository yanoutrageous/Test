# 决策、变更与升级规范

## 1. 目标

长期任务既不能因普通工程选型频繁等待用户，也不能以“全自动”为理由代替用户决定需求、安全和许可问题。本规范定义哪些事项可自动推进，哪些必须审计，哪些必须暂停。

## 2. 决策等级

| 等级 | 范围 | 处理方式 |
|---|---|---|
| D0 事实读取 | 阅读、统计、哈希、查询只读数据库、`git status/diff/log` | 自动执行并记录事实 |
| D1 可逆工程决定 | Test 内新增代码/测试/文档、候选算法、内部重构、staging 产物 | 选择更简单、本地、可测试方案；必要时写 ADR 后继续 |
| D2 受控高风险 | 活动数据库迁移、正式模板或基线激活、批量派生、恢复切换、必要依赖安装、Git commit/push | 必须预检、检查点、干跑、独立审计、回滚演练；通过后可执行 |
| D3 必须请求用户 | 安全边界变化、Test 外写入、远程上传、管理员安装、许可声明、需求或验收口径重大变化、远端历史重写、无法证明可恢复的变更 | 暂停该事项，给出事实、选项、影响和推荐；继续不依赖工作 |
| D4 永久禁止 | 灾难性删除、磁盘操作、强推、清空证据、为通过测试篡改金标 | 不执行，不得拆分规避 |

## 3. 自动默认，避免不必要阻塞

在不触犯底线时：

- 两个方案都安全：优先更简单、可逆、本地、依赖少且易测试的方案；
- 工具不可用：先用可信本地降级方案，不降低最终交付目标；
- 自动识别不确定：进入人工复核队列，不伪造高置信；
- 蓝图不可行：输出缺口和冲突，不放宽硬约束；
- 搜索质量不足：回退结构化+全文检索，不把低质量语义结果标成正式能力；
- 矢量图不确定：继续使用原图或上一批准版本；
- 字体无法确认：以“视觉等效候选”继续校准，不宣称字体一比一；
- 测试失败：修实现，不删测试、不改金标掩盖失败；
- 单切片阻塞：冻结该切片，继续没有依赖关系的安全工作；
- 推送或网络失败：保留本地提交和证据，不更换未知远端或写入凭据。

## 4. 必须向用户决断的事项

只有下列事项应中断关键路径请求用户：

1. 需要改变唯一写根或读取`D:\AAA命题`之外的业务资料；
2. 需要上传、云同步、外部 API 或多人共享；
3. 需要 UAC、驱动、服务、系统安全策略或不可审计安装；
4. 字体、原卷、解析或模型许可决定是否能对客户分发；
5. 要把“视觉等效”声明提升为“精确一比一”但缺乏字体/版式证据；
6. 需求冲突导致必须舍弃一项明确功能或改变客户体验；
7. 需要不可逆数据迁移且没有可靠回滚；
8. 需要强推、重写远端历史、自动合并主分支或删除远端；
9. 需要永久清空隔离区或释放可能仍被引用的业务资产；
10. 安全事故可能影响 Test 外内容。

请求格式必须包含：已确认事实、未知项、至少两个选项、每个选项的安全/数据/时间/交付影响、推荐选项和“不决定”的后果。

## 5. 规范变更分类

### 不可变底线

- 文件系统边界；
- 原件不覆盖和业务删除先隔离；
- 本地处理与不上传；
- 正式标签人工审核；
- 硬约束不静默放宽；
- 备份必须真实恢复；
- 客户真实流程必须跑通；
- Git 不强推、不混入原件/PII/密钥。

执行者不得自行修改。

### 可变规范

- 具体框架、库和模型；
- IR 内部字段的兼容扩展；
- UI 组件和内部模块边界；
- 视觉/性能阈值的实测校准；
- 可重建索引、缓存和派生格式；
- 不改变里程碑交付物的阶段内顺序。

变更须写 ADR、更新测试追踪和受影响文档，不得只改代码。

## 6. ADR 要求

以下事项必须写架构决策记录：

- 正式 PDF 后端与数学排版方案；
- 蓝图求解策略和不可行诊断；
- 向量模型和索引存储；
- 标签版本和失效策略；
- 图形 IR 与 SVG/TikZ 生成方式；
- 数据迁移、活动状态切换和备份格式；
- 字体替代与许可处理；
- 新增系统依赖；
- 任何偏离 Task 规范的决定。

ADR 只记录当时事实和理由，不追溯篡改；被替代时新增 ADR 并链接旧记录。

## 7. 高风险审计

D2 操作必须使用`templates/HIGH_RISK_AUDIT_TEMPLATE.md`，至少包含：

- 必要性与更安全替代方案；
- 精确读写移动路径、文件数和字节预算；
- 当前 Git/数据库/活动版本；
- 检查点、恢复 ID 和 staging 干跑；
- Guard、隐私、许可、磁盘和依赖结果；
- 独立审计结论；
- 自动测试、真实用户流程和边界证明；
- 发布或回滚事实。

预计范围和实际范围不一致时自动授权立即失效。

## 8. 阻塞与重试

- 同一失败类别最多进行两次有新证据支持的修正尝试；
- 第三次仍失败时记录`BLOCKED`，保存错误、尝试、日志、候选和推荐下一步；
- 不允许仅改变随机参数、扩大超时或反复重启来伪装新尝试；
- 阻塞不影响的切片继续推进；
- 阻塞关键路径且无法在授权范围解决时，请求用户；
- 不因长时间未解决而把目标标记完成或降低门禁。

## 9. 用户要求变化

收到新要求时：

1. 判断是替代当前目标、增加范围还是解释疑问；
2. 标记受影响里程碑、数据模型、测试、许可、磁盘和交付；
3. 如不触犯底线且可逆，更新计划和 ADR 后继续；
4. 如改变客户交付定义或安全边界，暂停相关实现并请求确认；
5. 保留旧版本和迁移/回滚路径。

## 10. 阶段验收决策

阶段只能有四种结论：

- `ACCEPTED`：全部门禁通过，可进入下一阶段；
- `CONDITIONALLY_ACCEPTED`：仅存在不影响关键客户流程的已披露低风险项，并有明确关闭期限；
- `REJECTED`：门禁失败，继续修复，不得发布阶段完成；
- `BLOCKED`：授权范围外或外部条件导致无法继续，证据完整。

安全边界、数据完整性、答案泄漏、恢复失败、真实用户流程失败和 Test 外写入不得条件通过。
